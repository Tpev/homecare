# Implemented care workspace: preservation map

September 8, 2026. This maps the local implementation to the [original preservation requirements](../find-care-screen-audit-2026-09-07/proposal/data-preservation-map.md), [one-time inventory](../find-care-screen-audit-2026-09-07/one-time-source-inventory.md), [recurring inventory](../find-care-screen-audit-2026-09-07/recurring-source-inventory.md) and [175-screen baseline](../find-care-screen-audit-2026-09-07/master-tracker.md). The original requirement table contains **31 information/action families**, followed by an independent-state matrix. The table below preserves those 31 families and treats that matrix as check 32; it does not invent a missing field family.

This is a source-to-destination audit, not proof that every populated field, every external service, or every possible state combination has been exercised in a browser. See the [capture method](method-and-coverage.md) for the separate evidence standard. Original screenshots are unchanged comparison evidence.

## Actual navigation and scope

- Unhired one-time request: Overview (`home`), Caregivers (`applicants`), Care details (`overview`), Help (`support`). The existing `overview` query key still opens the original care details.
- Unhired recurring request: Overview, Caregivers, Visits (`visits`, requested weekly pattern), Care details; Get help remains a contextual action. There is no fabricated plan before the existing hire/activation service creates one.
- Continuing recurring care: Overview (`overview`), Caregivers (`caregivers`), Visits (`visits`), Care details (`details`), contextual Message and Get help.
- A booked recurring occurrence: This visit (`shift`), Care instructions (`overview`), Help & changes (`support`), plus its parent-care breadcrumb. Original explicit `applicants` links remain supported for recruitment history even though they are not a second caregiver-navigation tab inside the dated visit.
- A one-time booked visit: Overview (`shift`), Caregivers (`applicants`), Care details (`overview`), Help (`support`).

The plan is resolved from **booking or request** `care_plan_id`. The original recurring request can also be the first booking; later generated requests remain one-time records linked to the plan. Parent links do not rewrite these records. Plan-to-visit links carry exact request ID, `tab=shift` or `support`, return tab, visit filter and pagination page. Parent return links restore these validated values and the visit-row anchor. Existing source URLs are not blanket-redirected.

## Final independent audit findings and limits

The source audit found two navigation regressions and one visibility gap, all corrected in the final source pass:

1. Switching tabs from an open hours/hire review left the decision panel visible. In particular, Question these hours switched to Help while leaving the approval CTA above it. Valid tab changes now clear only the preview flags and retain draft inputs.
2. A past-date unbooked request kept the legacy `overview` primary key, which now means Care details; its Choose another date task was on `home`. Unbooked requests now default to `home`, including past-date requests, while explicit legacy detail links still work.
3. Moving the full profile to Care details also moved safety information previously visible above every request tab. The new `visit-care-essentials` partial now exposes compact attached-snapshot safety/access/contact content on scheduled/live Overview, while the complete profile remains in Care instructions.

The plan's declined/expired status pill also now uses the existing neutral terminal-state colors. Only the color condition changed; action eligibility and lifecycle state remain untouched. Guided-support anchors were restored by root as a separate compatibility fix.

Capture coordination found one additional scope distinction: **full plan event history is not a visible implemented destination**. Details displays the care reference, schedule version and lifecycle dates; Visits displays schedule-change requests; Care story displays derived lifecycle stages. The original plan Blade also did not render `CarePlanEvent` reasons/payloads. Preserving these database records is therefore supported, but a claim that their complete contents are available in a new expanded Details disclosure would be inaccurate unless that disclosure is explicitly added and verified.

The recurring home also corrects a pre-existing display limit: unresolved extra reports cannot disappear behind 12 more recent reports. Its test covers 14 reports, including an older pending one, with unchanged persisted report state.

These are presentation findings. No new service authorization, time calculation, payment capture, cancellation, matching, profile-sharing or notification rules are part of this implementation. Existing service limitations are not silently repaired or represented as new guarantees. An example is schedule acceptance cancelling all future scheduled plan bookings from the effective date, including extras; the new copy reflects that existing behavior.

## Evidence needed to call the 175-screen comparison complete

The requirement is **all 175 original screen IDs on desktop and mobile: 350 baseline device views**, plus added plan tabs and confirmation states. Each expanded disclosure/tab remains a distinct state. A complete baseline run must have no missing or failed baseline IDs in `baseline-coverage.json`; the new screenshot/inventory validator must also pass. Each device has viewport, focused viewport, full-page image and visible field/control inventory.

`check-baseline-coverage.mjs` checks captured/device presence. That check alone does **not** prove the named lifecycle state still matches the stored booking/plan/status or that every field is present. Validate state labels against fixture identity and independent status axes, particularly pending/countered plans, scheduled versus missed check-in, reviewed with outstanding payment/correction, and ended with retained next visit. Synthetic dates are retained from September 7, so elapsed-time copy can change without any data mutation. Record such differences rather than relabeling the baseline as newly seeded evidence.

`data-preservation.json` is the separate read-only business-row comparison of baseline and copied local databases. It must show no removed/changed baseline business fields and an unchanged baseline DB hash. This proves fixture preservation, not every UI field's visibility or real processor behavior.

Coverage does not automatically extend to all source-only branches in the [original recurring audit](../find-care-screen-audit-2026-09-07/proposal/recurring-audit.md): external card authentication, provider maps, device/location permissions, delivered communications, all report/correction financial combinations, all direct-offer states, effective schedule boundaries and continuous-care flows still require their own explicit evidence. New synthetic countered/declined/cancelled plans and new UI previews add evidence, but do not close unrelated source-only gaps.
