# Data and action preservation map

September 7, 2026. This is a proposed UI organization, not a migration or implemented behavior. The current [one-time inventory](../one-time-source-inventory.md), [recurring inventory](../recurring-source-inventory.md) and each [master tracker](../master-tracker.md) row remain the field-level baseline. Screenshot values are synthetic examples; preserve the fields and meanings, not those sample values.

## Proposed navigation

**September 8 refinement:** the [recurring navigation proposal](recurring-navigation-proposal-2026-09-08.md) now recommends one continuing recurring-care home with Overview · Caregivers · Visits · Care details, contextual Message/Get help, and dated visit details inside that care's context. It supersedes the recurring navigation structure described below. The information/action preservation rows remain requirements; Help stays accessible through the contextual entry, and each visit retains its own snapshot, record and action history.

For each request or dated visit: **Overview · Caregivers · Care details · Help**, in that fixed order. Overview contains the current task, operational information and the dated visit's record/activity. Caregivers shows recruitment before hire and the chosen caregiver first afterwards, while retaining past replies and invitations. Help stays visible even when a specific action is unavailable; it should explain availability and offer only existing supported routes.

For a recurring plan: **Overview · Visits · Care details · Help**, in that fixed order. Overview contains plan status, attention, live/next visit and the agreement summary. Visits contains upcoming, cancelled and past occurrences with direct dated-visit links and existing schedule management. The chosen caregiver is in the header/Overview with a link to the relevant caregiver context. Generated recurring occurrences use the same dated-visit workspace as one-time care and have a parent-plan breadcrumb.

Message caregiver is a direct contextual action to the existing conversation. No new Activity, payment or review tab is required. Keep the existing global Overview/Arrangements/Schedule/History navigation at the cross-care level; distinguish its scope from a local workspace. Existing deep links should continue to resolve to equivalent destinations if routing is later changed.

## Non-negotiable preservation rules

1. **Shorten the first screen by changing hierarchy.** Do not delete populated fields, suppress historical records, replace exact values with an unexpandable summary or hide unresolved decisions in collapsed content. Desktop and mobile expose the same authorized information and operations.
2. **Preserve separate state axes.** Request status, plan status, booking status, time submission, family approval, correction/report status, payment/refund state and review existence are independent. A friendly stage label is derived from these values; it does not overwrite or conflate them.
3. **Preserve record identity.** Request ID, booking/visit ID, parent plan ID, visit kind, source links, conversation, schedule version, profile version, actors and timestamps stay attached to the original record. Displaying “Recurring visit” must not mutate generated `request_type=one_time` records.
4. **Keep urgent information visible.** Show actionable safety/support items, current visit state, payment issues, pending hours/corrections/reports, pending change responses and relevant care safety/access/contact essentials near the top, including counts when several exist. One primary CTA does not mean only one visible issue.
5. **Preserve permissions and timing.** Moving a family-visible profile field does not grant candidate caregivers access to assigned-only information. Keep existing ownership/account boundaries, action eligibility, deadlines, confirmation requirements and late/no-show consequences.
6. **Keep history truthful.** A withdrawn request, cancelled/no-show/disputed visit or ended plan remains retrievable. A pending correction cannot make a receipt claim that corrected hours were confirmed. A plan can end while its next visit and remaining financial/review work continue.

## State presentation contract

| Independent source state | Truth the interface must preserve | Example acceptable presentation |
|---|---|---|
| Request open with invitations, no application | Inviting is different from reviewing an application | “Waiting for replies · 2 invitations sent” |
| Hired application, booking absent | Selected is different from successfully scheduled | “Caregiver selected · visit setup pending” |
| Plan pending/countered | Proposed dates are not booked care | “Waiting for Sofia” / “Sofia proposed a new schedule” |
| Plan active + scheduled visit | Plan generates/maintains ongoing care; visit has a date | “Recurring plan active” plus “Wednesday visit scheduled” |
| Plan active + future pause date | A pause is scheduled, not already in effect | “Active · pause starts September 14” |
| Plan paused + one paused/completed visit | Agreement pause and operational visit state are separate | Plan “Paused”; dated visit keeps its own state and pending work |
| Completed visit, submitted/unconfirmed time | Care ended; family approval/payment work remains | “Visit finished · review 2h of care” |
| Hours approved, payment action required | Time approval remains saved | “Hours approved · confirm payment” |
| Active correction + old payment/receipt | Prior record and proposed adjustment are distinct | “Corrected hours need review” with separately labeled prior paid amount |
| Payment authorized/captured/refunded | Held, charged and returned funds differ | “Card authorized” / “Paid” / “Partially refunded · net paid …” |
| Family review absent/present; caregiver review absent/present | Feedback is independently optional/available | “Leave a review” or each existing review, without fabricating the other |
| Plan ended, next retained | Ending the series does not cancel every dated commitment | “Plan ended · next visit still scheduled for September 9” |

The copy above illustrates the proposed presentation; it must be derived from the existing source state and current supported flow, never written back as a substitute status.

## Snapshot and access-control feasibility notes

`CareRecipientProfilePresenter::forCareRequest()` and `forCarePlan()` read the profile version attached to the request/plan. Family users who can access the record receive the assigned snapshot. Eligible unassigned caregivers receive the candidate snapshot only in the supported open/pending/countered contexts; selected caregivers receive the assigned snapshot only in supported booking/plan states. This proposal is a family-workspace redesign and does not expand those permissions.

The “Updated” profile badge is currently driven by caregiver view tracking in `assigned()`, not a universal family-facing indication that the latest live profile changed. Keep its real meaning. If a new “Latest profile differs” banner is desired for families, that is a separately defined comparison/choice, not reuse of the current badge without checking semantics.

The recurring plan has its own pinned recipient, address and task snapshots. Generated occurrence requests inherit the relevant plan data and profile version; bookings also have agreement snapshots. The request and plan page can therefore legitimately differ from a later editable profile. Show the care context/version used for this agreement or visit; never rewrite past notes, locations, tasks or rates because the global profile changed.

Plan Help and plan caregiver links should reuse existing authorized destinations. There is no evidence in this review of a dedicated plan-wide incident/dispute service equivalent to the dated-visit forms. Until such a flow is explicitly designed, a plan Help view should select the affected visit or open existing general support; it must not submit a visit dispute against an arbitrary next booking. Similarly, route Message caregiver to the verified existing conversation/source context rather than guessing from a name or creating a new record.

## Later implementation acceptance check

Every current screen ID should map to a proposed destination, with its populated fields, controls, errors and action availability checked against desktop and mobile. Verify collapsed details open correctly, tab/deep-link state persists, and a notification from History/Schedule/plan attention lands on the exact booking/report/correction. Prioritize the source-only/external branches in the [recurring audit coverage list](recurring-audit.md) before calling the redesigned flow complete. Compare screenshots and visible-control inventories; visual tidiness alone cannot prove that data was preserved.
